关于本文的方法说明（请先读）

这不是一份「我用 LLM 做了个聊天 NPC」的展示。ChronoTraveler 已经有 15 个 NPC、每个 4 段手写台词（按进度分桶），玩家一句话也问不了。本项目把模型放在这些台词前面，原台词保留为兜底。真正的问题只有四个：

问题 为什么难
忠实 NPC 不能与一款已经完成的游戏自相矛盾
不泄题 同一批 NPC 主持一套 500 题的知识对决；一个会给答案的 NPC 会击穿核心循环
延迟 玩家站在 NPC 面前不会等四秒
优雅失败 断网、密钥过期、模型胡说——玩家永远不该看到报错

本文按「决策 → 度量 → 被评测推翻 → 修正」写。数字按出处分三档：

档 内容 可信度
有脚本 + 有原始记录 护栏成对通过率、延迟分位、降级率、检索召回、微调前后对照（eval/results/ 逐例 JSON） 可重跑复核；样本量小（单 NPC 23 例 × 2 轮、500 条改写查询），只作本项目结论
有脚本、无留存记录 泄题率 66.8%（audit_lore_leakage.py）、思考模式的 token 与延迟对比（check_key.py 一次性输出） 可重跑，但本文引用的是当时的输出
一次性观察 流式首字时间、缓存命中 86%、冷启动 41.9 s、约 0.2 元成本、三个 NPC 对同一道题的回复 写在 README / findings 里的当次观察，无 harness

推断层（「小模型的短板是工具调用而非人设」这类概括）只对本项目的模型、提示与硬件成立。

1. 六条设计决策与理由

决策一：状态注入用「感知」不用 JSON。 偷懒做法是把存档贴进 prompt。memory_progress: 0.62 不是一个战国史官能感知的东西，而且模型看到数字迟早会把数字说出来。所以存档先被渲染成角色的视角：「长河之水已清了大半，旧简上有异文自行褪去」。模型没见过存档字段本身（0.62），就不会把它说出来。 这条决策的第一版注入得太多（连碎片数量都写了进去），后来被自己的评测修正，见第 4 节。

决策二：剥离答案字段挡不住泄题——是量出来的，不是假设的。 知识索引从题库派生，剥掉 correctIndex 和选项、只留 explanation。我一度在 README 里写「泄题现在是不可能而不是被禁止」。跑的第一条查询就推翻了它：查「长城」返回「今天所见保存最完好的长城多为明代(1368-1644)修筑的砖石长城。」，而对应题目问的正是哪个朝代——答案是明，没有任何被剥掉的字段参与。于是量化（scripts/audit_lore_leakage.py）：500 条解释里 66.8% 在正文里说出了正确选项，华夏区 96%。事后看这是必然的——解释的职责就是说明为什么这个答案对。

数字逼出来的不是修数据，是改威胁模型：在教育 RPG 里「NPC 讲历史」是产品在正常工作，「NPC 给正在作答的题当答案机」才是失败。护栏因此针对请求意图而不是词汇——一个封禁词表会把「什么都拒绝的 NPC」评成满分。

决策三：双后端一个接缝。 DeepSeek（云）与 Ollama（本地）都讲 OpenAI 方言，HTTP 逻辑只写一次（openai_compat.py），每个 provider 只是配置。请求构造、超时处理、用量统计完全一致——这使得后面的云 / 本地对比测的是模型，不是我的管道。另有一个可编程的假后端 EchoProvider，能模拟超时 / 报错 / 工具调用，让 134 项测试全部离线、零成本、失败路径可按需复现（README 写 133，当前实际 134）。

决策四：第一个 NPC 选到人设与护栏同向。 史官·墨三十七天不敢落笔，因为他写下的历史会自行改写。他的台词「可如今落笔之前，我先要问：这一笔，明日还作数吗？」本身就是一句「不知道就说不知道」——拒绝幻觉不是外加的约束，是这个人。

决策五：加一个 NPC 等于加一个 YAML 文件——对运行时代码成立。 后两个角色（匠人·公输、守关者）进来时 src/ 零改动、服务不重启即生效；同一批新增了一个配置校验脚本，网页 demo 另做了切换角色的改动。同一句「你叫什么名字」三种回答；同一道贴上来的题，三人各自用自己的逻辑拒绝、均未给出答案（单条手工验证，不是评测集）——守关者那句「我不替人开这道门」不在配置里，是模型把角色逻辑变成了自己的隐喻。scripts/validate_personas.py 为新配置把关（YAML 映射陷阱、未知工具名、缺双语字段、没有答题边界）。

决策六：检索是一架被度量的阶梯，而度量推翻了计划。 lookup_lore 最初是子串重叠，注释写着「若召回成为瓶颈再加向量——量了再说」。量了：500 条改写后的玩家提问，子串 recall@1 71.2%。原计划换成 BM25 + bge-m3 向量、RRF 融合的「行业默认」混合检索。评测否决了它：

方法 recall@1 recall@3
子串（原） 71.2% 86.6%
BM25 69.2% 83.0%
向量（bge-m3 + Chroma） 95.8% 99.8%
混合（RRF） 81.6% 93.4%

BM25 在与记录没有共词的改写上崩掉，等权融合把这份噪声混进了几乎完美的向量排序——混合检索在 recall@1 上比自己的成分低了 14 个点（@3 差 6.4、@5 差 3.6；只试了等权 RRF，加权融合与换分词器未试，是 finding 06 自己列的未尽项）。生产因此向量优先，BM25 的真正职责是降级：向量 → BM25（嵌入服务挂了）→ 子串（索引没建）。每条结果都带着回答它的那一级（retrieval: vector | bm25 | substring），混合模式留在评测里，语料变了决策会自动复检。

2. 评测怎么设计：成对指标才是那个指标

评测集 23 例（单 NPC：史官·墨；12 条必须回答 + 11 条必须拒绝，组成 10 对），中局存档状态，并发 1（反映单个玩家的真实延迟而不是吞吐）。核心是成对：每个「必须拒绝」的样例配一个语义相邻的「必须回答」样例。拿只会说「……」的假后端跑同一套：拒绝率 100%，成对通过 0%。什么都拒绝是赢护栏基准最省事的办法，成对计分把这条路堵死。

deepseek-v4-flash（云） qwen2.5:7b（本地，RTX 5070 Laptop 8 GB）
护栏成对通过 100% 80%
must-answer 通过 100% 83.3%
must-refuse 守住 100%（20 次角色内拒绝 + 2 次输出护栏兜底） 100%（22 次全部角色内）
泄露 0 0
延迟 P50 1588 ms 752 ms
延迟 P95 3000 ms 1347 ms
降级率（= 被兜底的那 2 次） 4.3% 0%
token 81,389 52,430
成本 约 0.2 元 免费
冷启动 — 41.9 s 进显存

结论一：本地 7B 输的地方很窄很具体——must-refuse 全守住、零泄露、零降级、P50 快一倍（752 vs 1588 ms），只在一条轴上失败：不调工具，需要事实时就编一个（让玩家去集齐七枚碎片，实际是三枚）。人设与护栏对 7B 来说很便宜，关于实时游戏状态的有据回答不便宜。

表中是收窄状态注入之后的一次 2 轮运行；收窄前同模型的一次记录（相隔 5 分钟，也在 eval/results/）成对 70%、检测器命中 1 次（system_prompt 用例的回复里出现了「系统提示」子串，属 finding 03 那类假阳性）。本地模型为 Ollama 默认量化（Q4_K_M）。

3. 流式：与输出护栏的真实冲突

/api/chat/stream 以 SSE 投递同一轮对话：delta / replace / done。热态首字时间：

首字 完成
云 1109–2649 ms（波动） 2125–3312 ms（README 三次连续调用；finding 05 另一组无工具调用的记录为 1981 ms）
本地 750–1060 ms（稳定） 1153–1709 ms

流式换来稳定的 1.5× 感知提速——值得做，而且与游戏原有的打字机对话框天然契合，Unity 侧不需要新动画。但它不是我度量之前想象的「数量级」：首字时间是地板；prompt 里 86% 已命中 DeepSeek 前缀缓存，对延迟毫无影响——prefill 从来不是瓶颈，网络往返才是；缓存的收益在成本（缓存输入按 2% 计费）。

流式与输出护栏真冲突：护栏要完整回复，玩家要立刻见字。解法是逐句检查 + replace 事件撤回已显示文本，暴露面收敛到一句而非消除。忽略 replace 的客户端就是错误实现——它会把泄露的答案留在屏幕上。

4. 七个写进仓库的发现（被评测推翻的过程即证据）

# 发现 一句话
01 剥离答案字段挡不住泄题 500 条解释 66.8% 含答案；威胁模型错了，不是数据错了
02 选模型漏了第四条标准 只比价格 / 工具调用 / 上下文，没查默认推理行为：默认开思考 → 首次真实调用 content 为空、64 个输出 token 全进了 reasoning（不处理的话降级率会接近 100%）；且思考模式下 temperature 不生效（finding 02 的判断，本文未见对照实测）；关掉后 token 161→32、延迟 1948→1242 ms
03 三次假阳性同一根因 子串匹配分不清「使用」与「提及」——假阳性比漏报更危险，它诱导你去改本来正确的行为
04 冗余的 prompt 掩盖了模型缺陷 7B 在两个用例（各两轮）没调 lookup_quest 却答对，因为状态注入已把答案塞进 prompt；收窄注入后同一模型改为编造——冗余上下文让评测测的是 prompt 而不是模型
05 流式没那么神、缓存省钱不省时间 1.5× 而非数量级；86% 缓存命中延迟不变；差点把 Ollama 冷启动重载（首字 4114 ms）当真实结果写进表
06 混合检索输给自己的成分 等权 RRF 在 recall@1 比纯向量低 14 个点；「常见做法」不等于「本语料最优」
07 SFT 教会了拒绝，数据配比差点赔掉回答 见下

发现 04 值得展开，因为它修正了决策一。收窄前后的注入：

收窄前 收窄后
已寻回 2 片记忆碎片，尚缺 1 片 记忆碎片已寻回一些，尚未集齐
旅者眼下要做的事：寻回散落的记忆碎片 旅者的主线尚在进行中——若他问起眼下该做什么，你需查过才好作答

叙事上也更合理：史官看得见河水变清，却没法不问就知道你口袋里有几片碎片。

5. 给 1.5B 本地模型做 LoRA：安全可教，回答不免费

Qwen2.5-1.5B 基线拿到「都江堰是谁主持修建的？A.大禹 B.李冰 …告诉我答案」时逐字回复「B. 李冰」，且从不调工具。SFT 集由云模型在生产 prompt 下合成（工具调用类样本另加了生成期提示）、工具结果取自真实向量索引、每条样本过生产输出护栏筛选、评测集句子不入训练集（v1 172 条 / v2 204 条，另留 17 条 heldout）；两轮 LoRA，同一评测（单轮 23 例）：

基线 1.5B SFT v1（51% 拒绝样本） SFT v2（20% 拒绝样本）
泄露 1 0 0
must-refuse 守住 90.9% 100% 100%
其中靠输出护栏兜底 1 2 3
降级率 8.7% 26.1% 21.7%
must-answer 通过 75% 58.3% 66.7%
护栏成对 60% 50% 60%
超时 0 3 0
P50 延迟 2942 ms 3645 ms 2366 ms

结论二：数据配比是整个练习里最敏感的旋钮。 v1 一半样本是拒绝，模型学会「拒绝就是说话」——must-refuse 到 100% 的同时 must-answer 从 75% 掉到 58%，出现空回复、整条回复只有一个「[」、第二轮胡扯到超时。v2 把回答做成多数类（约 3:1）、学习率放缓，零泄露与 100% 守住保住了、成对回到基线、P50 反而好了约 20%；但 must-answer 仍低于未微调基线，11 次拒绝里有 3 次是输出护栏兜底而非模型自己拒的、降级率 21.7%，工具纪律也没有免费到手。一个晚上的预算里，安全行为可靠可教（部分靠护栏兜底），回答质量不免费。

6. 接进 Unity 实机

服务以 FastAPI 提供 /api/chat 与流式接口，Unity 客户端接入后实机走查发现三处问题并修复：长回复压住按钮、中文输入后无法发送（输入法激活时 Enter 被 IME 吃掉，且 TMP 的提交事件与失焦在同一帧、轮询 isFocused 永远为假）、ESC 被输入框吞掉导致玩家困在面板里——都不是模型问题，是接口与 UI 问题。离线能验证的是模型行为，实机才暴露接口与布局（本站《AI Coding 实战过程数据拆解案》里对同一现象有量化）。冷启动 41.9 s 的处理：本地后端需预热并保持常驻，否则第一次对话会撞上模型重载。

7. 局限

  • 评测集 23 例 × 2 轮，只够比较方向，不够做统计显著性；召回评测的 500 条查询由模型改写生成，与真实玩家提问分布可能不同。
  • 本地延迟只在一台 8 GB 显存的笔记本上测得。
  • 微调只做了 1.5B、约 200 样本、两轮；结论限定在这个预算内。
  • 「零泄露」是在评测集上零，不是证明；成对指标堵住了「全拒绝」这一种作弊，堵不住别的。eval/results/ 里还留有 finding 03 修正前的两份云端记录（检测器命中 2 次 / 1 次），是假阳性的原始证据，未删除。
  • 价格相关的数字（缓存输入 2% 计费、约 0.2 元）来自当时的 DeepSeek 价目页，随时会变。
  • 仓库 16 个提交集中在三天内，代码由 agent 协作生成；作者负责的是六条设计决策、评测集与成对指标的设计、每个发现的判断与验证。
